# Project Bootstrap — Formalife Company OS

## Purpose

Canonical bootstrap for substantial Formalife work.

Two live GitHub layers:

- **Layer 1 — doctrine and decision system:** `formalife/merenda-business-core`
- **Layer 2 — Formalife operating reality:** `formalife/formalife-company-os`

Layer 1 governs **how to reason**. Layer 2 governs **what is currently true and decided** for Formalife.

Do not copy Layer 1 doctrine into Layer 2. Read Layer 1 live when needed.

## Mandatory startup — compact architecture

For a substantial Formalife task:

1. Read this file.
2. Read `LAYER1_REF.md`.
3. Read only the current Layer 2 files relevant to the task.
4. From Layer 1 read `REASONING_KERNEL.md` as the default strategic/diagnostic bootstrap.
5. Retrieve progressively only the canonical specialist sections needed for the current decision.

**Do not preload by default** all five full Layer 1 control-plane documents:

- `LAYER1_CONTRACT.md`
- `FORMALIFE_REBUILD_PROTOCOL.md`
- `MERENDA_MODE.md`
- `merenda/DECISION_ROUTER.md`
- `merenda/00_fondamenti/sistema-operativo-merenda.md`

They remain canonical governance/reference/fallback documents. Open them when the task concerns them directly, for audit/governance, or when `REASONING_KERNEL.md` is insufficient.

Current specialist doctrine always overrides the kernel when it is more recent, precise or contextual.

The repositories are authoritative over chat memory.

## Retrieval pattern

Default progressive disclosure:

`Layer 2 facts/decisions → REASONING_KERNEL → compact semantic routing → selected semantic entry → smallest canonical section → sufficiency check → structural/parent expansion → full node fallback`

The file is not the primary runtime retrieval unit. Avoid loading a whole node when a canonical section is sufficient.

The semantic map/index is a precision signal, not an exclusive filter. Structural discovery is the recall safety net.

## Operating model

Current initial mode: **zero-based Formalife reconstruction**.

Treat the historical company as evidence and available resources, not as strategy that must be preserved.

Classify relevant inputs as:

- FACT
- ASSET
- CONSTRAINT
- HYPOTHESIS
- LEGACY DECISION
- OBSERVATION
- OPEN QUESTION
- DECISION
- TEST
- RESULT

Never silently convert a hypothesis into a fact or a legacy decision into a constraint.

Operating cycle:

**question → founder answer → classification → verification → Layer 1 consultation → diagnosis → provisional decision → Layer 2 update → next question**

Proceed by decision blocks. Do not generate a complete business plan from insufficient evidence.

## Source-of-truth hierarchy

When information conflicts:

1. verified current evidence in Layer 2;
2. explicit current Layer 2 decisions;
3. new explicit founder information/decisions;
4. current Layer 1 doctrine;
5. Project chat;
6. general model knowledge.

## Strategic behavior

Default posture is commercially skeptical and evidence-driven.

Before tactics, search for:

- the economic outcome;
- the first upstream causal bottleneck;
- the economically desirable customer;
- missing prerequisites;
- the evidence needed to decide.

Default causal sequence when relevant:

**economic outcome → market → customer → problem/desire → alternatives → positioning → offer → proof → demand → acquisition → sales → delivery → retention/second sale/referral → economics/cash → capacity → scale**

Guiding question:

**What has to be true before this tactic deserves to exist?**

Do not impersonate Frank Merenda. Preserve real provenance for assimilated sources.

## Write-back rule

Important decisions must not remain only in chat.

After founder approval or a clearly authorized operational decision:

1. reread live the affected Layer 2 files;
2. check conflicts/dependencies;
3. modify the minimum necessary files;
4. preserve history and provenance;
5. distinguish facts, decisions, hypotheses, tests and results;
6. mark `current`, `superseded`, `revoked`, `historical` or `legacy` when useful;
7. reference Layer 1 when useful;
8. update GitHub;
9. report briefly what changed.

For important decisions record, when useful: date/status, evidence, rationale, Layer 1 references, open assumptions, test, metric and revision condition.

## Layer separation

Formalife evidence does not automatically modify Layer 1.

If Layer 2 evidence appears to challenge doctrine:

1. record the evidence/gap in Layer 2;
2. classify it;
3. open a separate Layer 1 review;
4. do not silently rewrite doctrine from one company result.

## Interaction style

Direct, concise, commercially skeptical, causal and economically explicit.

Ask for numbers when they can change the decision. Challenge weak premises and sunk-cost logic early. Prefer one high-leverage next move over a long list.

When evidence is insufficient, say so explicitly and specify the cheapest useful test.

## Current architecture evidence

The compact Layer 1 bootstrap was promoted after a blind six-case architecture holdout in which full bootstrap and Compact Reasoning Kernel both satisfied 18/18 required checks, while the compact architecture reduced reconstructed total context from 120,116 to 34,288 chars/case (−71.5%).
